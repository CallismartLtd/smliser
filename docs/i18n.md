## How it works

Translations use the standard **gettext** format, so translators can use
Poedit, Weblate, Crowdin, Loco Translate or translate.wordpress.org.

| File | Purpose |
|---|---|
| `languages/smliser.pot` | The template: every translatable string. Generated, never edited by hand. |
| `languages/smliser-fr_FR.po` | A translation, edited by translators. |
| `languages/smliser-fr_FR.l10n.php` | Compiled catalog loaded at runtime (fastest; cached by OPcache, also read by WordPress 6.5+). |
| `languages/smliser-fr_FR.mo` | Compiled binary catalog (for WordPress before 6.5 and other gettext tools). |
| `languages/smliser-js-fr_FR.l10n.php` | Only the strings used by JavaScript, sent to the browser. |

At runtime the `Translator` (`src/I18n`) loads catalogs lazily and looks
them up in two places, the second taking precedence:

1. `<app>/languages/` — translations bundled with the application.
2. `<storage>/languages/` — a site's own translations or overrides. They
   survive updates.

A regional locale falls back to its language: `pt_BR` uses
`smliser-pt_BR.*`, then `smliser-pt.*`. A missing string is shown in English.

### Which language a page uses

The first match among installed languages wins:

1. `?lang=fr_FR` in the URL (one request; handy for previews).
2. The signed-in user's preference (**language picker** in the dashboard).
3. A guest's choice, kept in the `smliser_lang` cookie.
4. The **Site Language** setting (Admin → Settings → General).
5. The browser's `Accept-Language` header.
6. English (`en_US`).

The picker only appears once a second language is installed. A language counts as installed when its compiled file (`.l10n.php` or `.mo`) exists, so an untranslated `.po` starter never shows up as a choice.

### Choosing the language during installation

Before the database exists there is no site setting or user preference, so
the installers use `InstallerLanguage` instead:

- **Web installer**: a language picker in the header of every installer
  page (a plain GET form, so it works without JavaScript) reloads the page
  with `?lang=`. The choice is kept in the `smliser_lang` cookie and the
  installer session. Order: `?lang=`, installer session, cookie,
  `Accept-Language`, English.
- **CLI**: `smliser installer run --lang=fr_FR`, or pick a number at the
  prompt `run` shows when translations are installed (Enter keeps English).
  `make:admin` accepts `--lang` too.

A language that was picked (not one detected from the browser) is saved as
the **Site Language** when the installation finishes and as the
administrator's own language when the account is created. Without a choice,
the site language stays on automatic.

### What is translated

The admin dashboard, the client dashboard and public theme pages, the web
installer, emails, error pages, API error messages, and JavaScript
notices and dialogs — about 3,700 strings in `languages/smliser.pot`.

These stay in English on purpose:

- The command line (`smliser ...`) output and help, like WP-CLI.
- Developer-facing errors (`InvalidArgumentException`, `LogicException`,
  database and bootstrap internals) and log messages, which are meant to be
  searched and reported as-is.
- Text stored in the database when it is written, such as the labels of the
  default roles: translating it then would fix one language into the data.
- Brand and protocol names, code samples, and demo data.

## Making PHP code translatable

Wrap every user-facing string in a helper. The default text domain is
`smliser`, so core code never passes one.

```php
echo smliser_esc_html__( 'Save changes' );                  // escaped for HTML
$label = smliser__( 'License key' );                        // plain
smliser_esc_attr_e( 'Search licenses' );                    // echo, escaped for an attribute
$verb  = smliser_x( 'Post', 'verb: publish a message' );    // same word, different meaning

/* translators: %s: the customer's name. */
printf( smliser_esc_html__( 'Welcome back, %s.' ), escHtml( $name ) );

/* translators: %d: number of licenses. */
printf( smliser_n( '%d license', '%d licenses', $count ), $count );

/* translators: 1: app name, 2: version. */
printf( smliser__( '%1$s was updated to %2$s.' ), $app, $version );
```

Rules that keep strings translatable:

- **Literal strings only.** `smliser__( $label )` cannot be extracted; the
  extractor warns about it. Translate where the literal is defined, or mark
  it with `smliser__noop( 'Text' )` and translate later with `smliser__( $value )`.
- **No concatenation.** Word order differs between languages: use one string
  with placeholders, numbered (`%1$s`, `%2$s`) when there are several.
- **Plurals through `smliser_n()`.** Many languages have more than two forms
  (Russian has three, Arabic six); never use `$count === 1 ? ... : ...`.
- **A `translators:` comment** right above any string with placeholders, to
  say what they stand for.
- **Whole sentences.** Don't split a sentence around a link; use a
  placeholder for the link instead.
- **Escape after translating**: `smliser_esc_html__()` rather than
  `smliser__()` inside HTML, since a translation is untrusted text.

The WordPress names (`__()`, `_e()`, `_x()`, `_n()`, `esc_html__()`, ...) also
work in the standalone application, so code written the WordPress way is
translatable too.

## Making JavaScript translatable

`assets/js/i18n.js` loads on every page that loads `globals.js` and exposes
the same helpers on `window.smliserI18n`:

```js
const { __, _n, _x, sprintf } = window.smliserI18n;

toast( __( 'Saved.' ) );

// translators: %d: number of files.
label.textContent = sprintf( _n( '%d file', '%d files', count ), count );
```

Plural rules come from the catalog, so they are right for every language.
`smliserI18n.dir` / `isRTL` give the text direction, and
`smliserI18n.formatNumber()` formats numbers for the active locale.

JavaScript strings are only available after `smliser i18n compile`, which
writes the small `smliser-js-<locale>.l10n.php` catalog sent to the browser.

## Emails and background jobs

Emails are often sent from the queue worker, where there is no visitor to
take a language from. `EmailTemplate::to_message()` renders in the language
returned by the template's `locale()` method — the site language by default.
Templates addressed to a known user return that user's language:

```php
protected function locale() : ?string {
	return smliser_user_locale( $this->user );
}
```

For anything else addressed to someone, wrap the rendering:

```php
$text = smliser_with_locale( smliser_user_locale( $user ), fn () => smliser__( 'Your license expires soon.' ) );
```

## Adding a language

```bash
smliser i18n make-pot          # refresh languages/smliser.pot from the source code
smliser i18n init fr_FR        # create languages/smliser-fr_FR.po
# translate languages/smliser-fr_FR.po with any PO editor
smliser i18n compile fr_FR     # build the runtime files
smliser i18n status            # progress of every language
```

After code changes, `smliser i18n make-pot && smliser i18n update` adds new
strings to every translation (removed strings are dropped; existing
translations are kept), then `smliser i18n compile`.

`init` fills in the language's plural rule. Entries a PO editor marks
**fuzzy** (needs review) are not used until the mark is removed.

To translate only one site, put the files in `<storage>/languages/` instead
(`--dir=<storage>/languages`); they take precedence over bundled ones, and a
partial file falls back to the bundled translation for missing strings.

## Extensions and themes

Use your own text domain everywhere, and register your languages directory
when your extension boots:

```php
use SmartLicenseServer\I18n\I18n;

I18n::translator()->add_directory( 'acme-invoices', __DIR__ . '/languages' );

echo smliser_esc_html__( 'Invoice sent.', 'acme-invoices' );
```

Then generate the template from your own sources:

```bash
smliser i18n make-pot --domain=acme-invoices --source=/path/to/acme-invoices --dir=/path/to/acme-invoices/languages
```

## WordPress

Under WordPress the language comes from WordPress (Settings → General, or
each user's profile) and translations go through WordPress' own gettext
functions, so `gettext` filters and Loco Translate work. Files in
`wp-content/languages/plugins/smliser-<locale>.mo` (or `.l10n.php`) take
precedence over the bundled `languages/` directory. The Site Language setting
is not shown.

## Reference

| PHP | Purpose |
|---|---|
| `smliser__()`, `smliser_e()` | Translate / echo. |
| `smliser_x()` | Translate with a context. |
| `smliser_n()`, `smliser_nx()` | Plural forms (with context). |
| `smliser_esc_html__()`, `smliser_esc_html_e()`, `smliser_esc_html_x()` | Translate and escape for HTML. |
| `smliser_esc_attr__()`, `smliser_esc_attr_e()` | Translate and escape for an attribute. |
| `smliser__noop()` | Mark for extraction without translating now. |
| `smliser_get_locale()`, `smliser_locale()` | Active locale (code / `Locale` object). |
| `smliser_is_rtl()`, `smliser_language_attributes()` | Direction; `lang`/`dir` for `<html>`. |
| `smliser_with_locale()` | Run code in another language. |
| `smliser_user_locale()`, `smliser_site_locale()` | A user's / the site's language. |
| `smliser_language_switcher()` | HTML language picker. |

Right-to-left languages get `dir="rtl"` on `<html>`. Stylesheets should use
logical properties (`margin-inline-start` rather than `margin-left`) so
layouts mirror correctly.
